Project Summary

This project demonstrates a Microsoft Entra Conditional Access security baseline design. The lab focuses on planning identity security controls that protect administrators, standard users, and sensitive groups while reducing the risk of accidentally locking out the tenant.

Live Conditional Access policy creation was limited by lab tenant licensing and billing profile setup, so this project is documented as a Conditional Access design, rollout, testing, rollback, and evidence package instead of a live production deployment.

Business Problem

Organizations need to protect user identities without creating unnecessary disruption or accidentally locking out users and administrators. Conditional Access helps enforce controls such as MFA, access restrictions, and legacy authentication blocking, but the policies need to be planned carefully before rollout.

A strong Conditional Access baseline should improve security, protect privileged users, support least privilege, document emergency access, and provide a safe testing and rollback path.

Why It Matters

  • Protects administrator and privileged accounts
  • Reduces account compromise risk through MFA
  • Blocks older sign-in methods that bypass modern controls
  • Prevents tenant lockout through break-glass planning
  • Supports safer rollout with report-only testing
  • Creates documentation for security reviews and audits

Planned Conditional Access Policy Matrix

  • Policy 1: Require MFA for Administrators
    Require privileged and administrator users to complete MFA before accessing cloud resources.
  • Policy 2: Require MFA for All Users
    Require standard users to complete MFA when accessing Microsoft cloud applications.
  • Policy 3: Block Legacy Authentication
    Block older authentication methods that do not support modern security controls.
  • Policy 4: Require MFA for Sensitive Groups
    Apply stronger access requirements to sensitive groups such as Finance, HR, IT Admins, and Contractors.
  • Policy 5: Break-Glass Account Exclusion
    Document emergency administrator account exclusions to reduce the risk of total tenant lockout.

Rollout Strategy

The planned rollout starts with documentation and report-only testing before enforcement. This helps identify possible user impact, sign-in failures, or policy conflicts before the organization turns on enforcement.

  • Document the policy purpose and target users.
  • Exclude emergency break-glass accounts.
  • Start in report-only mode where available.
  • Review sign-in results and expected impact.
  • Test with pilot users or groups before broad rollout.
  • Move to enforcement only after validating expected behavior.

Rollback Plan

A rollback plan is important because Conditional Access mistakes can block legitimate access. The rollback plan gives administrators a safe recovery path if a policy causes unexpected issues.

  • Keep at least one emergency break-glass account excluded.
  • Document who can disable or modify the policy.
  • Record the policy settings before changes.
  • Disable the policy if it causes unexpected access issues.
  • Review sign-in logs and adjust conditions before re-enabling.

Break-Glass Account Planning

Break-glass accounts are emergency administrator accounts used when normal administrator access is unavailable. They should be carefully protected, monitored, and excluded from certain policies so the organization does not lose all administrative access.

  • Use a dedicated emergency administrator account.
  • Exclude it from Conditional Access policies that could block access.
  • Protect it with strong credentials and monitoring.
  • Restrict usage to emergency situations only.
  • Review and document access regularly.
